Сервер сайта «Дружба»
=====================

Рядом должна находиться папка `druzhba-dry-cleaning` с копией сайта. Для локального просмотра нужен Python 3.11+:

```sh
python3 server.py --port 8080
```

Стартовая страница — http://127.0.0.1:8080/. По умолчанию Т-Касса отключена. При локальной проверке используйте вымышленные данные. Для отдельного пути к сайту и базе укажите `--www` и `--db`. В базе SQLite хранятся только новые заявки, заказы, попытки платежей и доставка уведомлений. Экспорт из Flexbe — отдельный закрытый архив. Используйте один экземпляр приложения на постоянном диске. Делайте консистентные резервные копии через SQLite backup, проверьте восстановление. Папка с базой, архивом и секретами не должна быть внутри `--www`.

Для тестового поддомена: запускайте приложение от отдельного системного пользователя, за HTTPS-прокси на 127.0.0.1. Прокси должен подставлять `X-Real-IP` из адреса клиента, ограничивать размер и частоту запросов, не кешировать обработчики заказа и не записывать параметры запроса с ключом просмотра заказа. `/healthz` проверяет связь с базой. Введите настройки из `.env.example` в закрытое хранилище или запустите процесс с файлом окружения, доступным только ему. Сгенерируйте `APP_IP_HASH_KEY` командой `openssl rand -hex 32`. Для публичного режима обязательны `PUBLIC_ORIGIN` (HTTPS, без пути) и оба ключа reCAPTCHA. После одной заявки с IP за пять минут следующая требует reCAPTCHA. Email и Telegram включаются отдельно после внесения реквизитов. Очередь повторяет недоставленные уведомления; при пропаже ответа стороннего сервиса уведомление может прийти повторно.

Т-Касса:
- `TBANK_MODE=test` использует тестовый терминал. Укажите пароль соответствующего терминала и протестируйте реальный адрес `/payments/tbank/notify` по HTTPS. `TBANK_API_BEARER` поддерживается отдельно, если нужен по условиям доступа к API. Страница успешного возврата — главная, как в Flexbe. Параметр возврата при неуспехе не передаётся. Новый NotificationURL передаётся для каждого нового платежа при `Init`.
- Сверьте настройки действующего терминала и фискализацию. Код поддерживает одностадийное списание и не передаёт `Receipt`, что соответствует выключенной настройке Flexbe. Не включайте рабочий режим, если сейчас используется двухстадийное списание или для существующих чеков нужны реквизиты из сайта. `TBANK_PRODUCTION_READY=1` выставляется только после сквозного теста и этой сверки.
- Карточные данные вводятся на странице банка. Только проверенный `CONFIRMED` со совпадающими суммой и номерами заказа и платежа переводит заказ в `paid`. Сервер подтверждает получение уведомления после записи в базу. Для новых попыток без ответа используются `GetState` и `CheckOrder`; неопределённая попытка блокирует повторное списание. Записи `payment_alerts` требуют сверки с кабинетом банка, их нужно подключить к мониторингу на хосте. Обновления по возвратам зависят от данных уведомления; расхождение суммы требует сверки.
- Перед переключением проверьте карты «успех», «отказ», повторное уведомление, задержанный ответ и появление чека в текущей кассе; сверьте старые незавершённые платежи. Рабочий терминал и настройки Flexbe во время подготовки не меняются.

Документация банка: [уведомления](https://developer.tbank.ru/eacq/intro/developer/notification/), [Init](https://developer.tbank.ru/eacq/api/init), [тестирование терминала](https://developer.tbank.ru/eacq/intro/errors/test-cases).

Заявки в CRM: `CRM_MODE=amo` отправляет новые заявки напрямую в amoCRM, `CRM_MODE=roistat` — через Roistat с ключом проксилидов. По умолчанию оба выключены. Сверьте действующий маршрут и получите ID воронки, этапа, ответственного и полей, прежде чем включать отправку. При прямом подключении в `CRM_FIELDS_JSON` нужно указать ID текстового поля `details`; остальные ключи — UTM, `roistat_visit` и необязательный `order_id`. В `AMO_ACCESS_TOKEN` укажите токен приватной интеграции. Приложение само не обновляет короткоживущие OAuth-токены. Статус `uncertain` в таблице `outbox` означает, что перед повтором нужно проверить историю CRM/Roistat. Подтверждение платежа не создаёт ещё одну сделку.

Документация: [amoCRM](https://www.amocrm.ru/developers/content/crm_platform/leads-api), [Roistat](https://help-ru.roistat.com/quick-start/Zagruzka_zajavok_v_Roistat/).

Расширенное оформление заказа
-----------------------------

На `/order/` появился компактный запуск выбора вещей. Категории, поиск, варианты и размеры ковра добавляют позиции в существующую корзину. Старые кнопки услуг используют ту же корзину. В ней можно указать желаемые адрес, дату и время вывоза либо согласовать их по телефону, выбрать Т-Банк, наличные курьеру или согласование оплаты с менеджером. Менеджер подтверждает выбранное время.

Поле JSON `druzhba_checkout` необязательно. Старые запросы форм продолжают приниматься. Для расширенного оформления сервер сохраняет выбранный способ и пожелания в полях заявки, которые передаются текущим обработчиком CRM. Нативные поля `product_id`/`variant_id` и прежние `productId`/`variantId` поддерживаются. Данные размеров после нативной сериализации корзины восстанавливаются по ID позиции перед POST, цену повторно считает сервер.

Для ковров, услуг с ценой «от» и тарифа за килограмм сумма предварительная, заказ сохраняется для согласования. Онлайн-списание по нему заблокировано состоянием заказа. Для одежды с окончательной ценой выбор Т-Банка открывает существующую банковскую оплату. Наличные и согласование с менеджером создают заявку с отдельным понятным подтверждением. Размеры и параметры оформления сохраняются в текущей корзине и черновике, имя/телефон/email — только в сессии вкладки до успешной отправки.

Локально проверены новая корзина и прежние формы, в том числе мобильная ширина 390 px, переход между страницами, дробная площадь ковра, ошибки и повторы. Серверные проверки находятся в `work/server-check/check_payments.py`, `http_flow.py`, `check_extended_checkout.py` и `check_native_cart_wire.cjs`. Банковские Init/уведомления и данные CRM проверены с синтетическими ответами. Реальный платёж и доставка в рабочую amoCRM требуют отдельного сквозного прогона после настройки сервера.
